# แผนประเมิน iPPG เทียบกับ PPG อ้างอิง

## เป้าหมาย

แยกสองคำถาม: (1) ประมาณอัตราชีพจรถูกต้องเพียงใด (2) สัญญาณตามจังหวะและรูปคลื่นอ้างอิงได้เพียงใด
ค่า BPM ค่าเดียวไม่บอกทุกอย่าง และ correlation ค่าเดียวก็ไม่ยืนยันความถูกต้องทั้งหมด
แผนนี้เป็นแนวทางทดลอง ยังไม่ได้คำนวณความสัมพันธ์ของคู่ข้อมูลใหม่ให้เป็นผล validation

## สิ่งที่โปรแกรมบันทึกอัตโนมัติแล้ว

รัน `run_ippg.py` และ `analyze_ground_truth.py` ตามปกติ แต่ละรอบได้โฟลเดอร์ใหม่ใต้ `outputs/signal_runs`

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| graph.png | ดูกราฟจากรอบนั้นก่อนจัดแนวหรือ normalize เพื่อเทียบ |
| signal.csv | ค่าแต่ละจุดของสัญญาณบน time grid ที่ใช้ประมวลผล |
| original_signal.csv (PPG) | แถวข้อมูล PPG, BPM ที่มากับไฟล์ และเวลาเดิมก่อนรวม duplicate/interpolate |
| spectrum.csv | ค่าความถี่และขนาด/กำลัง FFT; แยกจาก signal เพราะจำนวนจุดและแกนต่างกัน |
| signals.npz | สัญญาณเต็มความละเอียดและแต่ละขั้นสำหรับ Python |
| manifest.json | config, sampling rate, ช่วงเวลา, time basis, source/code/file hashes และสถานะ export |
| RESULT.md | ค่า BPM และคำอธิบายไฟล์ |

iPPG เก็บ raw POS, reconstructed หลัง DWT, filtered หลัง band-pass และ RGB ที่ใช้ด้วย
raw POS ไม่ใช่ข้อมูลเซ็นเซอร์ดิบ และ RGB ในชุดนี้ผ่านการจัด grid ตามโค้ด extraction แล้ว
PPG เก็บ source timestamps ก่อน normalize ไว้ด้วย และคงจุดเวลาซ้ำในไฟล์ original_signal.csv
ไฟล์กราฟและค่าตัวเลขบันทึกก่อนเปิดหน้าต่างแสดงผล; เมื่อ export ล้มเหลว manifest จะไม่ระบุ complete

## ลำดับวิเคราะห์ที่แนะนำ

### 1. ตรวจว่าเป็นข้อมูลที่เทียบกันได้

- จับคู่คนและรอบการบันทึก; ชื่อคล้ายกันอย่างเดียวไม่เพียงพอ
- อ่านวิธีนิยามเวลาและ sampling rate ของสองฝั่ง ตรวจเวลาเริ่ม calibration, duplicate และ gap
- ถ้าชุดข้อมูลมี timestamp ที่กำกับเฟรมโดยตรง ให้ตรวจความสัมพันธ์นั้นก่อนใช้เวลา frame/FPS
- กำหนดช่วงเวลาร่วมที่มีข้อมูลจริง ห้าม extrapolate และห้ามตัดเฉพาะช่วงที่ผลดูดี
- ยังไม่เรียกข้อมูลว่า synchronized หากมีเพียงเวลาที่เริ่มนับจากศูนย์เหมือนกัน
- ห้ามใช้ตัวคูณ 34/32 กับชุดใหม่โดยไม่มีหลักฐานที่มา

### 2. ดูกราฟซ้อนและความสัมพันธ์ของรูปร่าง

- ดูทั้งช่วงเต็มและช่วงขยายที่กำหนดไว้ล่วงหน้า
- เก็บภาพ/คะแนนบนเวลาเดิมก่อนเสมอ
- ทำสำเนาสำหรับแสดงผลที่ลบค่าเฉลี่ยและหารด้วย std (Z-score) เพราะ amplitude ของ POS และเซ็นเซอร์คนละหน่วย/สเกล
- รายงาน Pearson r แบบมีเครื่องหมายบนข้อมูลที่จับคู่เวลาได้; r ต่ำหรือเป็นลบอาจเกี่ยวกับ lag/polarity และไม่เท่ากับ BPM ผิดทันที
- การ normalize ทำให้เปรียบเทียบรูปคลื่นได้ ไม่ได้พิสูจน์ว่า amplitude ของอุปกรณ์ถูกต้อง
- หากจะชดเชย lag ให้กำหนดขอบเขตล่วงหน้า รายงาน lag และคะแนนก่อน/หลังแยกกัน ระบุหากกลับ polarity
- lag ที่ fit เพื่อเพิ่ม correlation เป็นการวิเคราะห์เชิงสำรวจ ไม่ใช้ยืนยัน hardware synchronization
- ไม่ยืด/หดเวลาหรือใช้ dynamic time warping เป็นคะแนนหลักเพื่อทำให้กราฟตรงกัน
- พิจารณา filter ต่างกันก่อนสรุป morphology: ปัจจุบัน iPPG order 6 / b-a filtfilt; reference order 3 / SOS filtfilt

### 3. เทียบว่าจังหวะตรงและคงที่หรือไม่

- แบ่งช่วงที่ยาวพอและกำหนดไว้ล่วงหน้า ทำกราฟ BPM ต่อช่วงของสองฝั่ง
- ตรวจยอด FFT คู่แข่ง ความสม่ำเสมอระหว่างช่วง และช่วงสัญญาณแบน/ขาด
- ทดสอบกรณีอย่าง DATA42 ด้วย ไม่พิจารณาเฉพาะคลิปที่ให้ผลดี
- ถ้าคุณภาพเพียงพอ ค่อยตรวจเวลาของแต่ละ pulse peak และระยะห่างแต่ละจังหวะ; รูปร่างคลื่นจากหน้า/นิ้วและตำแหน่ง peak อาจต่างกัน
- ไม่อ้างความแม่นยำ HRV/IBI จากความใกล้ของ FFT BPM และต้องประเมินความละเอียดเวลา/วิธีหายอดก่อน

### 4. สรุปความคลาดเคลื่อนกับ reference ที่ตรวจสอบแล้ว

| ตัวชี้วัด | คำถามที่ตอบ |
|---|---|
| HR MAE (BPM) | โดยเฉลี่ยค่าชีพจรห่างจาก reference เท่าไร |
| HR RMSE (BPM) | มีช่วงผิดมากที่ส่งผลต่อภาพรวมแค่ไหน |
| Signed bias (BPM) | มักวัดสูงหรือต่ำกว่าฝั่งอ้างอิง |
| Bland–Altman ของ HR | ส่วนต่างกระจายแค่ไหน และเปลี่ยนตามระดับ HR หรือไม่ |
| Waveform Pearson r | รูปคลื่นบนเวลาและ normalization ที่ระบุสัมพันธ์กันแค่ไหน |
| Normalized waveform RMSE | รูปคลื่นที่ปรับสเกลแล้วต่างกันแค่ไหน (ไม่ใช่หน่วย BPM) |
| Yield / failure rate | วัดได้กี่คลิป และมีคลิปไหนถูกปฏิเสธหรือคำนวณไม่ได้ |

SNR หรือ coherence ใช้เสริมได้ภายหลัง โดยต้องกำหนดวิธีคำนวณและความยาวข้อมูล ไม่ตีความเป็นเปอร์เซ็นต์ความแม่นยำโดยตรง
correlation ของ HR กับ correlation ของ waveform เป็นคนละตัวชี้วัด ต้องแยกชื่อและหน่วยให้ชัด
ช่วงที่ซ้อนกันหรือหลายช่วงจากคนเดียวกันไม่ใช่ผู้เข้าร่วมอิสระหลายคน; การสรุปความไม่แน่นอนควรคำนึงถึงคน/คลิป
แยกคนสำหรับปรับแต่งกับทดสอบ และแสดงผลรายคน รวม failures ก่อนอ้างว่าระบบใช้ได้กับผู้ใช้ทั่วไป

## ขอบเขตข้อสรุป

ยังไม่มีคะแนนเดียวที่แปลงเป็น "iPPG ถูกต้อง X%" ได้โดยไม่กำหนดความหมาย เกณฑ์ และชุดทดสอบ
คลิป subject1 เพียงคลิปเดียวมีประโยชน์สำหรับตรวจ workflow แต่ไม่เพียงพอสำหรับสรุปความแม่นยำทั้งหมด
ขั้นต่อไปที่เหมาะคือโหลดสอง run ที่บันทึกไว้ ตรวจ time basis แล้วสร้างกราฟซ้อนและรายงานช่วงเวลาร่วม โดยเก็บค่าก่อนจัดแนวไว้
